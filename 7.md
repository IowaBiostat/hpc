# qsub

OK, the preliminaries are out of the way and we are now ready to use the batch scheduler for its main purpose: submitting jobs to be run on the compute nodes.  The command for this is `qsub`, and we will illustrate its use with the `sim.R` file from [earlier](i.html).  Let's create an executable shell script that runs `sim.R`:

{% capture _code %}
#!/bin/bash
Rscript sim.R
{% endcapture %}
{% include file.html name="sim" code=_code %}

We can test this locally:

{% capture _code %}./sim{% endcapture %}
{% include prompt.html code=_code %}

which creates a file like `sim-a3f9bx2k.rds`.  At this point, let's log out of our BIOSTAT node back into a login node (if you ran the above command from a login node, don't worry about it -- this simulation isn't particularly computer-intensive.  But in general it is very important to avoid running simulations on the login nodes).

<div markdown="1" class="alert alert-danger" role="alert">
If this didn't work, keep in mind that Windows and Linux have different file endings; [see here for further details](2.html#transferring-files-windows).
</div>

Running this simulation on a compute node is (almost) as easy as submitting `qsub sim`.  However, before we do this, we need to mention two important arguments to `qsub`.  One is `-cwd`, which says that we want to run the command in our current working directory; another is `-q BIOSTAT`, which specifies the queue; and a third is `-j y`, which joins the error and output logs into a single file (rather than creating separate `.e` and `.o` files).  So, let's run the simulation on a compute node:

{% capture _code %}qsub -cwd -j y -q BIOSTAT sim{% endcapture %}
{% include prompt.html code=_code %}

After a little while, a file like `sim-a3f9bx2k.rds` will appear.  You may also notice that a file like `sim.o1002669` appeared (your number will be different).  This contains a log of the output and any errors from your submission.  Typically it is not interesting (in this case it should be empty), but it is valuable when debugging or when your script prints important information.

Rather than type all these options out every time, I placed the following alias in my `.bash_profile` file (`...` indicates that this is not the entire `.bash_profile` file; there are more lines above and below this one):

{% capture _code %}
...
alias q_sub="qsub -cwd -j y -q BIOSTAT"
...
{% endcapture %}
{% include file.html name="~/.bash_profile" code=_code %}

The commands in `.bash_profile` are run at each login, but we can force them to run now with:

{% capture _code %}source ~/.bash_profile{% endcapture %}
{% include prompt.html code=_code %}

You don't ever have to do this again; it will happen automatically from now on when you log in.

Now, running our simulation on a compute node really is as easy as submitting:

{% capture _code %}q_sub sim{% endcapture %}
{% include prompt.html code=_code %}

To specify that the job requires multiple cores, or that it runs on specific cores, use the `-pe` and `-l` flags as discussed on the [previous page](6.html).
