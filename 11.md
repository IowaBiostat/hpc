# Snakemake

For simple jobs and array, `qsub` on its own is all you need. But once a job has multiple dependent steps, it's worth using a workflow manager to keep track of what depends on what and to resubmit only what's actually out of date. [Snakemake](https://snakemake.readthedocs.io/en/stable/) is a popular choice, especially in R/Python-heavy analysis pipelines, and it works very well in HPC environments.

# Installing Snakemake on the hpc

Snakemake is a Python package (hence the snake thing). There's a module for it, but the version is extremely old, so I recommend installing your own copy with [uv](https://docs.astral.sh/uv/) instead:

```bash
curl -LsSf https://astral.sh/uv/install.sh | sh
uv venv --python 3.13 ~/.venv
uv pip install --python ~/.venv/bin/python snakemake
uv pip install --python ~/.venv/bin/python snakemake-executor-plugin-cluster-generic
```
{: .prompt}

Then either run the following code or add it to your profile so that it's always available:

```bash
source "$HOME/.venv/bin/activate"
```
{: .file data-name=".bash_profile"}

# The Snakefile

Recall `sim.R` and `combine.R` from [earlier](0.html). Both already accept optional command-line arguments alongside their default, hash-based behavior --- `sim.R` takes an output filename, and `combine.R` takes an output filename followed by the input files to combine. That was set up with exactly this page in mind: it means neither script needs to change at all to run under Snakemake, and you can keep debugging them locally with a plain `Rscript sim.R` even after adopting Snakemake for the cluster runs. Snakemake just needs to be told to invoke them with the right arguments:

```python
container: "r-ver_latest.sif"

REPS = range(1, 11)

rule all:
    input: "results.rds"

rule sim:
    output: temp("sim-{rep}.rds")
    shell: "Rscript sim.R {output}"

rule combine:
    input: expand("sim-{rep}.rds", rep=REPS)
    output: "results.rds"
    shell: "Rscript combine.R {output} {input}"
```
{: .file data-name="Snakefile"}

We give the output filename a wildcard, `{rep}`, and ask for 10 different values of it with `expand()`. Snakemake sees that `combine` needs 10 files it doesn't have yet, works out that each one comes from a separate run of the `sim` rule, and submits all 10 as independent jobs, each running `Rscript sim.R sim-<rep>.rds` --- the same `sim.R` as always, just told which filename to use instead of inventing a hash. Once all 10 exist, `combine` runs `Rscript combine.R results.rds sim-1.rds sim-2.rds ... sim-10.rds`: again the same `combine.R`, just handed its file list directly instead of having to glob for it.

Marking `sim`'s output `temp()` tells Snakemake to delete each `sim-{rep}.rds` once `combine` has consumed it. `combine.R`'s own cleanup step only runs when it's called with no arguments, so there's no conflict between the two.

Note that the Snakefile also specifies which [container](9.html) to use.

# The Snakemake profile

Snakemake needs to be told how to submit jobs through `qsub`, and how to run everything inside our container. This configuration goes in a profile, which is a directory containing a file named `config.yaml`. Let's create a directory called `sge/` (for Sun Grid Engine) and put this config file there:

```yaml
executor: cluster-generic
jobs: 50
cores: 50
latency-wait: 60
printshellcmds: true

software-deployment-method:
  - apptainer

cluster-generic-submit-cmd: "qsub -terse -cwd -j y -q BIOSTAT -pe smp {threads}"
```
{: .file data-name="sge/config.yaml"}

`-terse` is required here (not just convenient): it makes `qsub` print just the job ID, which is how Snakemake tracks each job's status.

**Note:** If you end up using Snakemake across multiple projects, it's worth putting this directory at `~/.config/snakemake/sge/` instead, so every project can reuse it with `--profile sge` without a copy sitting in each one.

# Running snakemake

```bash
snakemake --profile sge --cores 2
```
{: .prompt}

What this code does:

1. Submit `sim.R` through `qsub` 10 times (each one through our container), making sure that it never uses more than 2 cores at a time
2. Once those jobs are all done running, `qsub` the `combine.R` script to combine the files into `results.rds`.

Why the code does this (Snakemake's logic):

1. The first rule (`all`) depends on `results.rds`
2. This doesn't exist, but Snakemake can see that it's created by the rule `combine`
3. `combine` depends on the existence of `sim-1.rds`, `sim-2.rds`, ..., `sim-10.rds`, which also don't exist
4. So it runs `sim.R` 10 times until they do, and so on back up the [DAG](https://en.wikipedia.org/wiki/Directed_acyclic_graph).

Meanwhile, setting the profile ensures that each job is run through `qsub` and `apptainer`. Note that the resulting `results.rds` object has 100,000 rows: 10,000 each from 10 different simulations.

This is not intended to be a full tutorial on Snakemake, but hopefully this example shows why the tool is useful and worth learning: it allows you to manage a complex chain of dependencies through simple rules describing the input and output of each step.
